Introduction

CLI baseline: The examples use Azure IoT CLI preview extension azure-iot 1.0.0b2, released 6 October 2026. Last reviewed against current Microsoft Learn guidance 5 November 2026. Release notes.

Welcome to this comprehensive blog series on building a real-world IoT device using Azure's latest IoT Hub, Azure Device Provisioning Service (DPS) features, along with Microsoft-managed certificate infrastructure.

What's changed since the previous preview?

I've refreshed the series to match the current preview. DPS is required, while certificate management is optional. The credential a device uses to get onto DPS is separate from the operational certificate ADR can issue for IoT Hub.

I've also moved the sorter to Microsoft's unified Microsoft.Azure.Iot.Device 2.0.0-preview4. ConnectionClient handles DPS and the Hub connection; TelemetryClient sends our Skittle readings. The custom C# provisioning protocol and legacy Microsoft.Azure.Devices.Client are gone. AzureDpsFramework stays as a thin configuration, durable CSR/key/issued-chain persistence, ADR ARM and session adapter. Microsoft's SDK design and feature matrix and unified examples are the starting points for the new API. The package is still a preview.

The series defaults to an X.509 bootstrap certificate for DPS and a CSR-issued X.509 operational certificate for the Hub. Standard symmetric-key/X.509 profiles and both CSR onboarding flows remain, along with .NET 10 and our existing Hub. The SDK discovers its assigned endpoint/profile through DPS. There's a bounded --cloud-self-test --config PATH for provision/connect/telemetry/disconnect without physical hardware. SDK retry/reprovision and optional IoT Hub renewal APIs are available, but automatic certificate renewal isn't implemented here. The sorter uses MQTTnet 5; the separate ADR software-updates client keeps MQTTnet 4 and its own DPS update protocol. The SDK doesn't implement that workflow. None of this requires an MQTT5 Hub or a cloud topology change.

The resource walkthrough now uses the current CLI flow and system-assigned identities, links DPS before IoT Hub, and creates an enrollment group linked to the ADR certificate policy. It doesn't create a device. You can also connect eligible existing services, but linking them is permanent.

I've clarified which credentials are for DPS onboarding and which are issued for IoT Hub. The policy belongs to an ADR intermediate CA and sets the operational certificate validity; this example uses a 30-day policy. The Microsoft-managed lifecycle includes renewal and revocation, with limitations for intermediate CAs signed by an external CA. I've kept the distinction between service capabilities, SDK APIs and the lifecycle code actually in this sample.

Preview Status and Current Guidance

Current preview status: Azure IoT Hub integration with Azure Device Registry (ADR) and Microsoft-backed X.509 certificate management remain in public preview and aren't recommended for production workloads. ADR is generally available for Azure IoT Operations; its integration with IoT Hub is still in preview.

ADR represents IoT Hub devices as Azure Resource Manager resources. Each IoT Hub links to one ADR namespace, and multiple hubs can share a namespace. You can create a new Hub or connect an eligible existing Hub. Connecting an existing Hub is permanent and can't be reversed; it doesn't interrupt Hubs that you leave unconnected. This series' setup script creates a dedicated new Hub. DPS is required for every IoT Hub preview scenario, whether or not you enable certificate management.

Certificate management is optional. It manages operational X.509 certificates used to authenticate to IoT Hub after onboarding with a separate credential. The device submits a CSR during provisioning; DPS validates the onboarding credential and coordinates issuance from the namespace's ADR certificate authority. The device's private key remains on the device. The locally created certificates in Part 4 are an example of an X.509 onboarding credential; they are separate from the ADR-managed operational certificate authority and policy.
