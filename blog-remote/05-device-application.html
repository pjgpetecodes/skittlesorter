The Device Application

CLI baseline: The examples use Azure IoT CLI preview extension azure-iot 1.0.0b2, released 6 October 2026. Last reviewed against current Microsoft Learn guidance 5 November 2026. Release notes.

In this post, we'll walk through the complete IoT device application that uses DPS provisioning with CSR-based certificate issuance. Rather than building from scratch, if you've not already done so, we'll clone the repository, run the setup automation, configure the application, and explore how the major components work together.

Current preview status

IoT Hub integration with Azure Device Registry (ADR) and certificate management remains in public preview and isn't recommended for production. The current getting-started guide supports creating a new Hub or connecting an eligible existing Hub; connecting an existing Hub is permanent and can't be reversed. The setup script in Part 3 creates a dedicated new Hub. DPS is required for every IoT Hub preview scenario. The current supported regions are Australia East, Japan East, Central US, and UK South. ADR integration and certificate management are free during preview, while IoT Hub and DPS are billed at standard rates.

Certificate management issues operational X.509 certificates after a device authenticates with a separate onboarding credential. The certificate policy belongs to an ADR intermediate CA and is selected on the DPS enrollment. ADR synchronizes CA certificates with linked IoT Hubs and manages CA lifecycle and rotation operations. SDK renewal APIs are available, but this application does not implement automatic operational-certificate renewal. See Microsoft's ADR connected-services guide, CA hierarchy, managed CA setup, and certificate-policy enrollment guide before creating or changing Azure resources.

What's changed in this version?

I've replaced the custom C# DPS provisioning protocol and the legacy Microsoft.Azure.Devices.Client with Microsoft's unified Microsoft.Azure.Iot.Device 2.0.0-preview4. One ConnectionClient handles provisioning and the Hub connection; TelemetryClient shares it for our Skittle readings. The sorter calls these SDK clients directly; AzureDpsFramework supplies configuration, durable credentials and optional ADR ARM helpers. Its existing session API remains for package compatibility.

Both standard symmetric-key/X.509 profiles and both CSR onboarding flows remain. .NET 10, our existing Hub and Azure resources are unchanged. The SDK discovers the assigned endpoint/profile through DPS, not a hostname constructed from the Hub name.

The new bounded --cloud-self-test --config PATH provisions, connects, sends representative telemetry and disconnects without physical hardware. SDK retry and reprovisioning are available, but automatic certificate renewal isn't implemented. Microsoft's SDK design and feature matrix and unified samples explain the new API. This is still a preview. See the Introduction for the series-wide changes.

Why Keep Credential Helpers?

I no longer need to maintain security providers, SAS tokens, registration polling or a DPS MQTT transport in C#. The official unified SDK handles those. Our helpers keep configuration, CSR/key and issued-chain files durable, and ADR ARM metadata operations out of the sorting loop. The sorter creates and uses the SDK clients directly.

Getting Started

Already completed previous posts? 

If you've already cloned the repository and run the setup scripts from the earlier posts, you can skip to Step 3: Configure the Application.

The steps below are for those starting fresh or who need to set up the complete environment.

Step 1: Clone the Repository (If Not Already Done)

If you haven't already cloned the repository from earlier posts, get the complete project code:

Clone the repository:

git clone https://github.com/pjgpetecodes/skittlesorter.git
cd skittlesorter

Step 2: Create the Azure Resources

Follow our updated Azure CLI walkthrough in Part 3 to create the ADR namespace, a new IoT Hub, and DPS in a supported region. The commands are aligned with the current Microsoft Learn Azure CLI deployment method. The script also creates the X.509 bootstrap certificate and enrollment. Part 4 explains those credentials and the separate operational issuer; its manual walkthrough is optional.

All IoT Hub preview scenarios require DPS. If using certificate management, configure a device onboarding credential separately from the ADR-managed operational issuer. Create an ADR intermediate CA and its certificate policy, then select that CA and policy on the DPS enrollment. Connect DPS before the Hub; ADR synchronizes CA certificates with linked Hubs. Keep the resulting DPS ID Scope, hub hostname, and onboarding credential for the application configuration.

Step 3: Configure the Application

Use the config written by Part 3: appsettings.002.json by default, or the path passed to -AppConfigPath. It already contains the DPS ID scope, registration ID, bootstrap certificate paths and CSR settings. Mock hardware is enabled, and the SDK discovers the assigned Hub through DPS. Review the configuration before running it; don't copy private keys into source control.

Key Configuration Sections:

  • DpsProvisioning: Bootstrap certificate paths and DPS connection details
  • DeviceId: Must match your registration ID
  • IssuedCertFilePath: Where the operational certificate chain from DPS will be saved
  • Hardware.MockMode: Enable hardware simulation for testing without physical devices

This is the X.509 + CSR profile from Part 4. For symmetric-key onboarding, select SymmetricKey and supply DeviceKeyBase64 (prefer a device-specific key over a group master key). Set RequestOperationalCertificate to false for standard symmetric-key or X.509 provisioning without issuance; the default stays true for compatibility with the earlier CSR examples.

Keep the CSR, matching key, issued chain and assignment sidecar across restarts. The generated profile keeps these separate from other enrollments. Paths retain the existing configuration resolution rules; don't package those files with an application release. The Part 3 setup script produces unified-compatible configuration with X.509 onboarding and CSR issuance enabled by default.

Build and run:

dotnet run --project .\skittlesorter.csproj -- --config .\appsettings.002.json

A Bounded Cloud Check Before Moving Anything

I like to prove the connection before involving the motors:

# Offline configuration check
dotnet run --project .\skittlesorter.csproj -- --self-test --config .\appsettings.002.json

# Real provisioning + Hub + representative telemetry, then disconnect
dotnet run --project .\skittlesorter.csproj -- --cloud-self-test --config .\appsettings.002.json

The cloud check has a two-minute bound and waits for one telemetry acknowledgement; it doesn't initialize physical sensors or servos. It does contact Azure, so use the intended subscription and identity. The helper scripts\iot-hub-device-registry\test-unified.ps1 -AppConfigPath PATH doesn't reset by default. Only use explicit -ResetDevice with matching resource names to reset that exact device/registration; it never deletes a resource group, enrollment group or CA. See the cloud-test runbook.

Reset also needs operator Hub data-plane registry read/delete permissions, such as scoped IoT Hub Registry Contributor, not just resource-management access. On a Hub with DisableLocalAuth=true, use Entra CLI authentication (--auth-type login); SAS is disabled. The helper checks Hub registry access before destructive work and stops if permission is missing. A successful device connection doesn't grant the operator registry access, so don't change RBAC unilaterally to force the reset through.

Verify in the Portal

Setting Up More Devices

To add another demo device, rerun the Part 3 setup command against the same services with a new -RegistrationId, -EnrollmentId and -AppConfigPath. The script creates a separate bootstrap issuer and credentials for that enrollment; it doesn't overwrite the first profile. Review the generated config and keep its private keys secure. If moving it to another machine, securely transfer the bootstrap certificate, key and chain, update their paths in the config, and run the bounded cloud check with that config first.

Troubleshooting Common Issues

Problem: "Failed to load bootstrap certificate"

Error: The system cannot find the file specified.
at System.Security.Cryptography.X509Certificates.X509Certificate2..ctor

Solution:

  • Verify AttestationCertPath, AttestationKeyPath and AttestationCertChainPath in the generated config point to the files created by setup.
  • If you moved the config to another device, update the paths to match.

Check certificate files:

$dps = (Get-Content .\appsettings.002.json -Raw | ConvertFrom-Json).IoTHub.DpsProvisioning
Test-Path -LiteralPath $dps.AttestationCertPath
Test-Path -LiteralPath $dps.AttestationKeyPath
Test-Path -LiteralPath $dps.AttestationCertChainPath

Problem: "DPS registration failed: Unauthorized"

DPS initialization failed: Registration failed with status: Unauthorized

Solution:

  • Verify your enrollment group exists in DPS
  • Check that CA certificates are uploaded and verified in DPS (see Understanding X.509 and CSR Workflows)
  • Confirm IdScope in appsettings.json matches DPS

Verify enrollment group:

az iot dps enrollment-group show `
  --dps-name "my-dps-001" `
  --resource-group "my-iot-rg" `
  --enrollment-id "my-device-group"

Verify CA certificates are verified:

az iot dps certificate show `
  --dps-name "my-dps-001" `
  --resource-group "my-iot-rg" `
  --certificate-name "my-device-root" `
  --query "properties.isVerified"

Problem: "Failed to connect to IoT Hub"

Error: The remote certificate is invalid according to the validation procedure

Solution:

  • Check that the ADR namespace links to DPS and IoT Hub have succeeded
  • Verify IoT Hub hostname matches assigned hub
  • Ensure operational certificate was saved correctly

Verify the ADR namespace links:

az iot adr ns link dps list `
  --namespace "my-adr-namespace" `
  --resource-group "my-iot-rg"
az iot adr ns link hub list `
  --namespace "my-adr-namespace" `
  --resource-group "my-iot-rg"

az iot dps linked-hub list checks the separate classic allocation links; an empty result doesn't mean these ADR namespace links are missing.

Problem: "Device already provisioned" but can't connect

If you see the operational certificate exists but connection fails:

Check the selected profile, saved chain, matching CSR key and assigned Hub first. Don't delete a shared certificate directory to fix one device. Use the reviewed exact-device cloud-test reset only when you intend to reprovision that identity.

Problem: Missing application configuration

Unhandled exception. System.Exception: IoTHub config missing

Solution:

  • Check that the generated config exists and that --config points to it. The default from Part 3 is appsettings.002.json; a custom -AppConfigPath changes that location.
  • If it was lost, inspect the existing enrollment and local credentials before rerunning setup. The script refuses to overwrite an existing enrollment or private key.

Problem: Certificate expired or renewal needed

Certificate Valid until: 2026-01-15 10:00:00Z (expired)

Solution:

  • Check the certificate policy, persisted chain and matching private key.
  • Operational certificate validity is set by the ADR certificate policy.
  • There is no automatic renewal scheduler in this application, and no service-wide seven-day renewal requirement. See the current certificate-policy guide and the service's renewal documentation.

The SDK offers optional IoT Hub renewal APIs without DPS reprovisioning. Using those safely needs a deliberate lifecycle implementation; deleting a certificate isn't the same thing. Preserve keys and chains while diagnosing.

Still having issues?

  1. Check Azure resources are properly configured (Creating DPS, IoT Hub and ADR Instances)
  2. Verify certificate and CSR setup (Understanding X.509 and CSR Workflows)
  3. Review Microsoft's ADR connected-services guide and certificate-policy enrollment guide for current resource and enrollment configuration
  4. Check DPS and IoT Hub logs in Azure Portal
  5. Enable verbose logging in appsettings.json:
{
  "Logging": {
    "LogLevel": {
      "Default": "Debug",
      "Microsoft": "Information"
    }
  }
}

Main Program Flow (src/Program.cs)

The main program still loads configuration, initializes mock or real hardware for a normal run, opens the cloud session and runs pick → detect → sort → drop. The cloud-self-test takes a separate bounded path and never initializes physical hardware. Shutdown disconnects the SDK session gracefully.

DPS Initialization Service (src/comms/DpsInitializationService.cs)

This service creates the SDK's ConnectionClient and TelemetryClient directly. ConnectionClient handles DPS registration and the Hub connection.

For CSR profiles, the identity helper loads or creates the durable CSR/key pair, supplies it to the SDK, then persists the returned operational chain with the matching key. The .connection.json assignment sidecar alongside the issued PEM lets restarts restore the operational certificate and assigned Hub. A required- certificate wrapper rejects a missing issued chain before Hub authentication. For standard profiles, it doesn't request a new certificate. The onboarding certificate and operational certificate remain different credentials; moving to an SDK hasn't merged their roles.

Application-specific helpers (AzureDpsFramework/)

I've kept the pieces specific to this application: configuration, device-key derivation where needed, certificate files and optional ADR ARM metadata helpers. The old session API remains for existing package consumers but isn't used by the sorter. The old security-provider, transport, registration and SAS-token protocol classes are removed, not wrapped.

For the SDK API itself, follow the official unified samples. For our file/configuration boundary, read the helper README.

For the default X.509 + CSR profile, our helper prepares the SDK inputs using the same callback-based pattern as Microsoft's authentication sample:

var authentication = new X509AuthenticationProvider(
    bootstrapCertificate, null, prepareCertificate, certificateChain: bootstrapChain);
var provisioning = new ProvisioningSettings(idScope)
{
    RegistrationId = registrationId,
    CertificateSigningRequest = new ProvisioningCertificateSigningRequest(operationalKey, csr)
};

Here csr is the base64-encoded DER signing request, and operationalKey is the persisted key that signed it. prepareCertificate validates the returned chain against that key and saves it; the private key stays on the device. The application wraps the provider with a guard so a CSR profile cannot fall back to the bootstrap credential if DPS returns no certificate.

The essential SDK calls look like this (with loaded configuration, coordinated MQTT options and a cancellation token):

using var identity = DeviceProvisioningIdentity.Create(dpsConfiguration);
using var connection = new ConnectionClient(connectionOptions, identity.LoadContext());
using var telemetry = new TelemetryClient(connection);
var context = await connection.ProvisionAndConnectAsync(
    identity.Provisioning, identity.Authentication, cancellationToken: cancellationToken);
identity.SaveContext(context);
// Send telemetry using telemetry, then disconnect.
await connection.DisconnectAsync(cancellationToken: cancellationToken);

The actual initialization service also cancels the SDK's retry when the required-certificate guard reports an issuance failure. The identity helper uses the SDK certificate callback to validate and save the issued chain before Hub authentication. The SDK samples keep the key in memory; our files preserve the identity across restarts. There's no custom register/poll loop.

Telemetry Service (src/comms/TelemetryService.cs)

TelemetryService now uses the SDK's TelemetryClient on the same connection. It preserves the application's JSON telemetry and message-property contract; we aren't changing cloud routes or introducing a second Hub connection. The optional session-count feature remains independent of this SDK migration.

Certificate Renewal

SDK retry/reconnection and reprovisioning are available through ConnectionClient. They aren't an automatic certificate-renewal scheduler. Optional IoT Hub renewal APIs are also available, but I haven't wired automatic operational-certificate renewal into this application. The old “delete the certificate seven days before expiry” snippet wasn't a complete lifecycle implementation, so I've removed it. Durable replacement and recovery need their own tests.

Azure Device Registry (ADR) Integration

Azure Device Registry provides device identity and metadata management that works with DPS and IoT Hub.

Key ADR Features

🔹 Device Metadata

  • Registry properties: manufacturer, model, hardware revision and software revision
  • Tags for custom labels such as hardware ID, location, tenant and environment
  • Enablement state: Enabled or Disabled

🔹 Credential Management

  • Policies for operational-certificate issuance
  • Certificate issuance, renewal, and revocation
  • CA lifecycle management, including automatic CA rotation

🔹 Multi-Hub Support

  • A namespace can be linked to multiple IoT Hubs
  • Devices are represented as Azure resources in the namespace
  • Query and govern resources across hubs sharing a namespace

Don't infer that moving a device between hubs avoids reprovisioning; follow the current DPS and IoT Hub documentation for device migration behavior.

ADR Client Implementation

The project includes an ADR client for device management (AzureDpsFramework/Adr/AdrDeviceRegistryClient.cs):

using Azure.Identity;
using AzureDpsFramework.Adr;

// Create ADR client (uses DefaultAzureCredential)
var adrClient = new AdrDeviceRegistryClient();

// List all devices in namespace
var devices = await adrClient.ListDevicesAsync(
    subscriptionId: "your-subscription-id",
    resourceGroupName: "my-iot-rg",
    namespaceName: "my-adrnamespace-uniquesuffix"
);

Console.WriteLine($"Found {devices.Count} devices:");
foreach (var device in devices)
{
    Console.WriteLine($"  - {device.Name}: {device.Properties}");
}

// Get specific device details
var deviceDetails = await adrClient.GetDeviceAsync(
    subscriptionId: "your-subscription-id",
    resourceGroupName: "my-iot-rg",
    namespaceName: "my-adrnamespace-uniquesuffix",
    deviceName: "my-device"
);

if (deviceDetails != null)
{
    Console.WriteLine($"\nDevice: {deviceDetails.Name}");
    Console.WriteLine($"Properties: {deviceDetails.Properties}");
    
    // Display tags
    if (deviceDetails.Tags.ValueKind == System.Text.Json.JsonValueKind.Object)
    {
        Console.WriteLine("Tags:");
        foreach (var tag in deviceDetails.Tags.EnumerateObject())
        {
            Console.WriteLine($"  {tag.Name}: {tag.Value}");
        }
    }
}

Configuration-Driven ADR Updates

Enable automatic device metadata updates in appsettings.json:

{
  "Adr": {
    "Enabled": true,
    "SubscriptionId": "your-subscription-id",
    "ResourceGroupName": "my-iot-rg",
    "NamespaceName": "my-adrnamespace-uniquesuffix",
    "DeviceUpdate": {
      "Enabled": true,
      "Attributes": {
        "manufacturer": "Raspberry Pi Foundation",
        "model": "Raspberry Pi 4B",
        "hardwareRevision": "1.4",
        "softwareRevision": "1.0.5"
      },
      "Tags": {
        "location": "factory-1",
        "department": "manufacturing",
        "hardwareId": "RPI4B-12345678"
      },
      "DeviceEnabled": true
    }
  }
}

The application automatically updates device metadata after provisioning.

There's one API detail worth calling out: the current ARM resource is namespaces/registryDevices (2026-11-02-preview), and it doesn't accept an arbitrary attributes object. Our Attributes configuration name is retained, but only exact keys manufacturer, model, hardwareRevision and softwareRevision are accepted and mapped to properties. Other keys fail explicitly; put custom labels in string-valued Tags, as with hardwareId above.

DeviceEnabled maps to enablementState: "Enabled" or "Disabled". The older OperatingSystemVersion configuration name is still accepted and maps to softwareRevision; if both are supplied, it overrides Attributes.softwareRevision. It isn't an ARM property of its own.

Testing the Complete Solution

Test 1: Verify Device in IoT Hub

Check device exists: This requires Hub registry read permission for your signed-in Entra identity; resource-management access alone isn't sufficient.

az iot hub device-identity show `
  --hub-name "my-iothub-001" `
  --device-id "my-device" `
  --auth-type login

Expected output:

{
  "deviceId": "my-device",
  "authentication": {
    "type": "certificateAuthority"
  },
  "connectionState": "Connected",
  "status": "enabled"
}

Test 2: Monitor Telemetry

The bounded cloud self-test waits for a representative telemetry acknowledgement:

dotnet run --project .\skittlesorter.csproj -- --cloud-self-test --config .\appsettings.002.json

For an interactive view of messages, use Azure IoT Explorer and its Hub connection string. This is separate from the device's X.509 authentication.

You can also watch incoming messages from a terminal using the Azure IoT CLI extension installed by the setup script:

az iot hub monitor-events `
  --hub-name "my-iothub-001" `
  --device-id "my-device"

Replace the names with your Hub and registration ID. Start monitoring before running the sorter, and press Ctrl+C to stop. The CLI uses a Hub shared-access policy to read telemetry and needs permission to retrieve its key; this is service-side access, not the device's X.509 credentials. Protect policy keys and use this option only on a Hub where shared access is enabled.

Test 3: Query ADR Devices

List devices:

az iot adr ns device list `
  --namespace "my-adrnamespace-uniquesuffix" `
  --resource-group "my-iot-rg" `
  --output table

Expected output:

Name        Location
----------  ----------
my-device   uksouth

Column selection can vary. Inspect JSON for properties.enablementState and the supported metadata properties; custom labels are under the resource's tags.
